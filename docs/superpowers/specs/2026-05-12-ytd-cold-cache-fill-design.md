# QDII Radar 今年来(YTD)冷缓存首个请求补算设计

## 背景
当前 `/api/funds` 采用快路径：慢字段优先读缓存，缺失时先返回占位值，再后台异步刷新。

把 `oneYearChange` 改为“今年来”后，冷缓存首个请求会出现：
- 接口日志已成功算出 YTD 并写入缓存
- 但当前这次响应仍返回 `oneYearChange=0`、`oneYearChangeAvailable=false`
- 用户要等下一次请求才能看到真实值

用户要求优化这个体验，但不希望把整个列表接口重新变慢。

## 用户确认
- 采用 **有限同步补算** 策略
- 阈值：**请求基金数 ≤ 3 时，同步补算今年来**

## 目标
1. 冷缓存下，少量基金请求首次也能拿到真实“今年来”
2. 保持 `/api/funds` 的整体快路径设计
3. 大批量请求仍避免被慢字段拖垮

## 非目标
1. 不取消后台异步刷新机制
2. 不把所有慢字段都改成同步补算
3. 不修改前端协议
4. 不新增 API 字段

## 方案
### 推荐方案：有限同步补算
在 `/api/funds` 中对 `oneYearChange` 缺缓存场景增加一个小阈值分支：

- 若缺失 YTD 缓存的基金数量 `<= 3`
  - 在当前请求内同步调用 `get_one_year_change()`
  - 将真实值直接写回当前响应
  - 同时仍写入缓存，后续请求直接命中

- 若缺失 YTD 缓存的基金数量 `> 3`
  - 保持现有行为：返回占位值
  - 后台异步刷新

## 详细设计
### 1. 触发条件
仅针对 `oneYearChange` / `oneYearChangeAvailable` 的缓存未命中情况。

判断方式：
- 收集 `missing_history_codes`
- 若 `0 < len(missing_history_codes) <= 3`，进入同步补算路径
- 否则沿用当前后台刷新路径

### 2. 同步补算行为
对 `missing_history_codes` 逐只调用：
- `get_one_year_change(code, is_exchange_traded)`

虽然 `is_exchange_traded` 现在已被 YTD 逻辑忽略，但继续传入可保持接口兼容。

拿到结果后，直接回填到当前 `funds` 响应对象：
- `fund["oneYearChange"] = result["percentage_change"]`
- `fund["oneYearChangeAvailable"] = result["available"]`

### 3. 与后台刷新关系
- **小请求（<=3）**：当前请求同步补算，不再把这些 code 交给后台刷新
- **大请求（>3）**：保持当前占位 + 后台刷新

这样避免一次请求里既同步又异步重复刷新同一批 code。

### 4. 性能边界
该策略只改善少量基金请求，不改变大列表表现。

预期效果：
- 单只基金请求：首次就有真实值
- 2~3 只基金请求：首次大概率有真实值
- 多只基金列表：仍然优先保证首屏速度

## 测试策略
1. **小批量缺缓存同步补算测试**
   - 1~3 只基金无历史缓存
   - 断言当前响应直接返回真实 `oneYearChange`
   - 断言不走后台 `schedule_history_refresh`

2. **大批量缺缓存仍异步刷新测试**
   - 4 只及以上基金无历史缓存
   - 断言当前响应仍返回占位值
   - 断言调用 `schedule_history_refresh`

3. **已有缓存不受影响测试**
   - 命中缓存时继续直接返回缓存值

## 风险与缓解
### 风险 1：小请求延迟上升
- 原因：同步补算要现算 YTD
- 缓解：严格限制在 `<=3`

### 风险 2：同步补算失败
- 原因：上游 AKShare/网络问题
- 缓解：保留当前容错逻辑，失败时返回 `available=false`

### 风险 3：重复刷新
- 原因：同步补算和后台刷新都打到同一批 code
- 缓解：小请求同步补算后不再调度这些 code 的后台刷新

## 验收标准
1. 冷缓存下，请求基金数 ≤ 3 时，当前响应直接返回真实“今年来”
2. 请求基金数 > 3 时，保持占位 + 后台刷新策略
3. 现有快路径测试不回退
4. `/api/funds` 返回结构不变

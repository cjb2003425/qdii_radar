# QDII Radar 性能优化设计（首屏快路径）

日期：2026-04-29

## 1. 背景

当前移动端访问 QDII Radar 首屏明显偏慢。已确认主要瓶颈不在前端包体，而在后端 `/api/funds` 首屏接口。

已验证事实：
- 前端主包约 269KB（gzip 81KB），不是 4~6 秒级卡顿的主矛盾
- `/api/funds` 重复请求耗时约 3.4s ~ 5.8s，且随基金数量增加而明显增长
- `/api/market-indices` 主要是冷缓存慢，热缓存后接近瞬时返回，不是持续刷新时的主问题
- 当前默认处理约 47 只基金

后端热点链路：
- `fetch_limits_for_codes()` 串行按 chunk=5 抓取 Eastmoney HTML 页面
- `fetch_single_fund_limit()` 同时解析限额和 NAV，必要时还回退到 AKShare
- `/api/funds` 返回前对每只基金同步调用 `get_one_year_change()`

这导致首屏必须等待所有慢字段都准备完成后才返回。

## 2. 目标

### 性能目标
- `/api/funds` 首屏接口目标：P50 < 1.0s，P95 < 2.0s
- 移动端首屏“加载中...”显著缩短，达到可接受交互速度

### 正确性目标
- 保持现有前端接口字段不变，避免前后端联调扩散
- 不回归已有 exchange-traded 修复逻辑：`isExchangeTraded` 仍然只能基于确认拿到真实行情后决定
- 慢字段允许延迟补齐，但页面不能报错、不能阻塞

### 稳定性目标
- 避免因优化引入对上游的刷新风暴
- 刷新失败时保留旧缓存或占位，不影响主流程可用性
- 保留快速回滚手段

## 3. 设计原则

1. 首屏优先：先返回用户最关心的核心行情字段
2. 慢字段降级：限额、1 年涨幅不阻塞主返回
3. 协议稳定：前端尽量 0 改动
4. 缓存优先：上游慢数据必须缓存化
5. 后台刷新：请求线程不等待慢刷新完成
6. 安全回滚：保留开关，必要时切回旧逻辑

## 4. 方案对比

### 方案 A（推荐）：单接口快返回 + 慢字段缓存/异步刷新

做法：
- `/api/funds` 保持原字段集合不变
- 首屏只同步获取核心行情
- `limitText`、`oneYearChange`、`oneYearChangeAvailable` 优先读缓存
- 缓存缺失或过期时先返回占位，再后台刷新

优点：
- 用户收益最大，能直接缩短首屏时间
- 前端基本无需修改
- 变更范围集中在后端编排层和缓存层
- 风险可控，容易加开关回滚

缺点：
- 部分字段在首次或缓存过期时会暂时为空/占位
- 需要补一个轻量后台刷新与去重机制

### 方案 B：保持单接口同步语义，但给慢字段全部加 TTL 缓存

做法：
- 仍在 `/api/funds` 内同步取 `limitText` 和 `oneYearChange`
- 只是优先读缓存，缓存 miss 时仍阻塞请求直到刷新完成

优点：
- 业务语义简单
- 前端完全无感

缺点：
- 首次访问或缓存 miss 仍然慢
- 无法从结构上解决“首屏等待慢活”问题

### 方案 C：拆成多个前端接口，前端首屏后再补拉慢字段

做法：
- `/api/funds` 只返回核心行情
- 新增 `/api/funds-extra` 或类似接口拉慢字段
- 前端做二次请求与局部刷新

优点：
- 边界更清晰
- 可长期演进为更合理的数据分层

缺点：
- 需要前端联动改造
- 当前阶段不是最小改动

### 推荐结论
当前优先采用 **方案 A**。它以最小改动解决主要矛盾，并保留未来向方案 C 演进的空间。

## 5. 目标接口行为

`/api/funds` 继续返回现有字段集合，不做破坏性协议变更。

### 核心字段（首屏必须同步返回）
- `code`
- `name`
- `valuation`
- `valuationRate`
- `marketPrice`
- `marketPriceRate`
- `premiumRate`
- `isExchangeTraded`
- `isWatchlisted` / 监控状态相关字段

### 慢字段（缓存优先，不阻塞首屏）
- `limitText`
- `oneYearChange`
- `oneYearChangeAvailable`

### 占位语义
- `limitText`
  - 有缓存：返回缓存值
  - 无缓存：返回 `"—"`（或沿用现有默认占位）
- `oneYearChange`
  - 有缓存：返回真实值
  - 无缓存：返回 `0`
- `oneYearChangeAvailable`
  - 有缓存：`true`
  - 无缓存：`false`

## 6. 后端架构调整

### 6.1 `get_qdii_funds()` 新流程

现状：
1. 拉 quotes
2. 拉 limits
3. 逐只算 `oneYearChange`
4. 全部完成后返回

目标流程：
1. 拉 quotes（保留现有核心行情获取逻辑）
2. 读取本地缓存的 `limitText`
3. 读取本地缓存的 `oneYearChange`
4. 立即组装 funds 返回
5. 对缺失/过期缓存，在后台触发刷新任务

### 6.2 新增缓存访问边界

为了避免把缓存/刷新逻辑揉进 endpoint，新增小边界函数：

- `get_cached_limit(code) -> { value, fresh, exists }`
- `refresh_limit_cache(codes) -> None`
- `get_cached_one_year_change(code) -> { value, available, fresh, exists }`
- `refresh_one_year_change_cache(codes) -> None`

要求：
- endpoint 只做编排，不直接承担慢抓取细节
- 慢数据的缓存规则和刷新规则集中在单独函数中

### 6.3 后台刷新机制

对于缓存缺失或过期的 code：
- 请求返回时不等待刷新完成
- 使用后台任务/异步 task 触发刷新
- 刷新完成后更新缓存

实现要求：
- 后台刷新失败只记录日志，不影响当前请求
- 如果存在旧缓存，失败后保留旧缓存，不清空

### 6.4 刷新去重

新增两类 in-memory in-flight 去重容器：
- `limit_refresh_inflight`
- `history_refresh_inflight`

规则：
- 某个 code 已在刷新中，则后续请求不重复发起同类刷新
- 刷新完成或失败后，必须释放 in-flight 标记
- 去重粒度以单个 code 为主，避免一键刷新把上游打爆

## 7. 缓存策略

### 7.1 1 年涨幅缓存
- TTL：1 天
- 原因：1 年涨幅不需要分钟级更新
- 复用现有 historical cache 思路和存储模型

### 7.2 限额缓存
- TTL：15 分钟（建议做成可配置）
- 原因：申购限额变化低频，但不宜缓存过久
- 目标：显著减少 47 个 HTML 页的重复抓取

### 7.3 HTML 中解析出的 NAV
- 不再作为首屏必须依赖
- 可保留为限额抓取链路中的附带信息来源
- 但不能让 `limitText` 抓取链路继续绑定首屏主流程

## 8. 前端影响

目标是前端 **0 改动或接近 0 改动**。

需要确认现有 UI 对以下状态能正常展示：
- `limitText = "—"`
- `oneYearChangeAvailable = false`

若现有 UI 已能兼容，则前端无需改动。

后续可选增强（不纳入本次最小方案）：
- 页面空闲后自动轻量 re-fetch 一次 `/api/funds`
- 用于快速补齐刚刚后台刷新的慢字段

这不是本次必要项，先不纳入首轮实现。

## 9. 变更范围

### 必改
- `server.py`
  - `get_qdii_funds()` 主编排逻辑
  - 限额缓存读写/刷新函数
  - 1 年涨幅缓存读取与后台刷新编排
  - in-flight 去重逻辑

### 尽量不改
- 前端接口协议
- `App.tsx` 首屏消费逻辑
- 现有 exchange-traded 判定修复逻辑

### 暂不处理
- `/api/market-indices` 的进一步优化（已有热缓存，非当前主矛盾）
- 前端拆接口重构
- 大规模通知系统/监控系统重构

## 10. 风险与应对

### 风险 1：慢字段首次为空
应对：
- 允许占位语义
- 保证核心行情字段优先可见

### 风险 2：后台刷新风暴
应对：
- TTL
- in-flight 去重
- 失败仅记录日志，不重复级联触发

### 风险 3：旧缓存不一致或过期逻辑混乱
应对：
- 将 cache read / refresh 逻辑收口到边界函数
- 明确 fresh / exists / fallback 语义

### 风险 4：回归既有场内基金修复逻辑
应对：
- 明确 `isExchangeTraded` 的语义不变
- 不允许把“候选资格”重新暴露成“确认可用”

## 11. 验收标准

### 性能验收
- `/api/funds`：P50 < 1.0s，P95 < 2.0s
- 本地连续刷新 3 次，响应明显低于当前 3.4s ~ 5.8s
- 手机首屏等待肉眼可见缩短

### 功能验收
- 页面核心行情正常显示
- `limitText`、`oneYearChange` 在无缓存时允许占位，但不报错
- 旧 exchange-traded 修复逻辑不回归

### 稳定性验收
- 多次刷新不应对同一 code 重复发起大量上游请求
- 后台刷新失败时，接口仍返回可用结果
- nginx 与直连 8088 路径行为一致

## 12. 回滚方案

增加开关，例如：
- `FAST_FUNDS_RESPONSE=true`

行为：
- 开启：使用“快返回 + 后台刷新”
- 关闭：回退到原有“同步算全再返回”逻辑

同时保留旧实现路径一段时间，便于快速对照与回退。

## 13. 实施结论

本次采用：

**将 `/api/funds` 改为首屏快路径接口，慢字段（`limitText`、`oneYearChange`）通过缓存返回，并在后台异步刷新；前端协议保持不变，优先实现后端最小改动与可回滚开关。**
